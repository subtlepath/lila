# Paginated content inventory

Version-one inventory requests carry: version u8, SD generation 16 bytes, snapshot revision u64, ordinal cursor u64, requested limit u8. All integers are little-endian. Revision zero starts a scan and requires cursor zero. Limits range from one to eight manifests.

Successful response page bytes carry: version u8, generation 16 bytes, nonzero revision u64, echoed cursor u64, next cursor u64, complete u8, manifest count u8, then that many 63-byte ContentManifest records. The fixed header is 43 bytes; eight entries occupy 547 bytes. The enclosing command response will carry its result byte separately. Nonterminal pages require at least one entry and next cursor equal to cursor plus count without overflow. Terminal pages require next cursor zero. Duplicate content hashes in a page are invalid. A shared fixture is in `protocol/fixtures/InventoryPage.json`.

`InventoryScan` enforces generation, revision, expected cursor, duplicate hashes across pages, and a caller-provided total-entry limit. Failed appends leave accepted state unchanged. It returns a complete `ReaderInventory` only after the terminal page. The request builder tracks revision/cursor across accepted pages. Authentication and connection binding must come from the session's inventory collector; this codec does not authenticate data itself.

`CompanionInventoryHandler.h` now implements bounded reader-side page construction over an `InventoryCatalog` interface. Catalog providers expose generation, nonzero revision, total count, and indexed manifest reads. The handler requires authorization, checks generation/revision/cursor, reads at most eight records directly into caller-owned response space, rejects duplicate hashes/invalid kinds, and rechecks generation/revision/count before returning success. No heap allocation or manifest array is introduced. Results are: 0 success, 1 invalid, 2 unauthorized, 3 wrong storage, 4 changed snapshot, 5 I/O failure. Error replies contain only the result byte.

`HalFile::prepareDirectoryEntry()` allocates one nothrow RAII handle before enumeration. This retains the existing opaque, mutex-protected SdFat ownership model rather than placing its implementation on the caller's stack. Repeated preparation adds no allocation. `directory.nextEntry(entry)` reuses the prepared handle, closes the previous entry through SdFat's openNext operation under the storage mutex, and returns `HalDirectoryResult::Entry`, `End`, or `Error`. Invalid/self-aliased/unprepared handles and sticky directory errors are rejected and logged. Stop on End; reopen the directory to retry a failed scan. No per-entry allocation is introduced by this API.

# Private cloud synchronization

The companion plan requires private CloudKit records/assets with CKSyncEngine, durable state serialization, account-change handling, quota/conflict reporting and offline local operation. The adapter and content asset exchange are not implemented yet. Pairing credentials stay exclusively in Keychain.

`LibraryStore.syncMutations(after:limit:resource:)` provides bounded immutable event/body pages for outgoing cloud or reader exchange. Limits are 1–250 records, with 128 by default. The SQLite identity index supplies deterministic byte-order traversal; the cursor is the last returned event identity, not a causal checkpoint or scheduler order. Complete scans must restart from the beginning to discover events arriving behind a cursor. Existing immutable event identity deduplication makes repeated delivery harmless, while equivocation remains an error. Incoming records must pass the existing body-hash, typed-history and course-family validation before insertion.

The pagination test checks reversed insertion, nonnumeric identity byte ordering, page bounds, complete body round trips, database reopening, resource filtering and discovery of late arrivals after restarting. All 168 CompanionKit tests pass. This establishes an exchange primitive, not operational CloudKit synchronization.

Apple references: [CKSyncEngine](https://developer.apple.com/documentation/cloudkit/cksyncengine-5sie5) and [CKSyncEngineDelegate](https://developer.apple.com/documentation/cloudkit/cksyncenginedelegate-1q7g8). Engine serialization must be persisted when state-update events arrive. The delegate must not invoke fetch/send methods from event handling, and outgoing record batches must respect CloudKit limits. Account changes must not silently upload retained data to a different account. Native SDK compilation and private-account integration testing remain required.

## Account-bound engine state

`CloudSyncStateStore` now persists versioned engine serialization in an atomic local JSON file, bounded to 8 MiB of serialization/12 MiB of encoded file data. One actor instance must own this file for the app lifetime. CloudKit account identities are opaque strings distinct from reader pairing credentials. Observing a different account, including sign-out, disables synchronization and discards the old checkpoint; explicit confirmation of the currently observed account is required to enable. Disabling the same account retains its checkpoint for subsequent resume. State writes update memory only after a successful atomic file replacement; malformed state is reported instead of silently resetting.

Tests cover restart, same-account observation, changed-account rejection of stale writes/confirmations, sign-out, disable/resume checkpoint retention, invalid account identities, corrupt files and injected file replacement failure. All 170 CompanionKit tests pass. The CKSyncEngine delegate, private content assets, entitlements/signing setup and native-account integration are still pending. This store does not upload data or change the local library.

## Journal delegate source

`CloudJournalSync` now implements a private-database CKSyncEngine delegate behind `canImport(CloudKit)`. It verifies the actual opaque account before starting, disables automatic engine scheduling, uses explicit fetch/send, persists serialized state updates and queues journal pages of 128 records. Record names are canonical event identity hex; `LilaJournalV1` records carry envelope and body data. The portable record codec validates envelope, body hash and name equality; incoming batches use the existing atomic library import. Identical immutable server-conflict records are acknowledged; conflicting content, record/zone deletion and other send errors stop the adapter and expose failure. Local causal history is retained. Failed incoming/outgoing validation prevents later checkpoint persistence. Concurrent manual synchronization is rejected, and late callbacks from replaced engines are ignored. Pairing credentials are never accessed.

All 171 portable tests pass. The delegate source passes frontend parsing, but Linux excludes CloudKit and therefore does not type-check or execute this adapter. Native SDK builds, event ordering/error/recovery integration tests, CKSyncEngine delegate state persistence failure injection, account/quota UI, CloudKit schema/entitlements, content metadata/assets and persistent outgoing acknowledgement optimization remain required before cloud sync can be enabled in the app. The app does not yet instantiate this adapter.

## App setup and verification

Settings now includes opt-in private journal controls: check the CloudKit account, explicitly confirm synchronization, inspect status/failure and disable. The app instantiates the adapter only when the processed `LilaCloudKitContainer` Info.plist key contains a configured `iCloud.` identifier. This key expands the `LILA_CLOUDKIT_CONTAINER` build setting. Undefined/empty settings leave cloud controls unavailable while the local library and reader operations remain usable. Cloud state initialization failures are contained independently of library initialization. Synchronization refreshes local library state after successful exchange. Automatic/background synchronization is not yet wired.

For a signed native build, choose your Apple development team and enable the iCloud capability with CloudKit for both app targets in Xcode. Select the same private container owned by that team and set `LILA_CLOUDKIT_CONTAINER` to its exact identifier in both targets/configurations. Xcode must generate/update the appropriate CloudKit container and services entitlements and provisioning profiles; the repository does not fabricate those account-owned identifiers. Preserve the Mac sandbox, file access and Bluetooth entitlements. Mac outbound networking is now enabled through `com.apple.security.network.client`. In the container development schema, journal records use custom zone/type `LilaJournalV1`, with Bytes fields `envelope` and `body`. Do not promote a production schema before native integration tests pass.

Verify iOS and Mac SDK compilation first, then use two installations in the same private development account: create local bookmark/history events, check/confirm the account on each, synchronize both, and repeat. Check deduplication, conflicting immutable payload rejection, interrupted fetch/state writes, quota exhaustion, unavailable network, account switching/sign-out and retention of offline reader operations. Inspect the persisted cloud state across restart. Source frontend parsing, string-catalog coverage and plist syntax pass on Linux; native compilation/signing, CloudKit execution and UI tests remain unverified. Content assets/metadata, course associations, global deletion propagation, outgoing acknowledgement optimization and background work remain unfinished.

## Durable journal acknowledgements

Schema 16 adds cloud journal receipts keyed by the SHA-256 of the opaque cloud account and immutable event identity, with a fingerprint covering envelope and body. `pendingCloudMutations` filters bounded scan pages against receipts and rejects mismatched immutable content. `acknowledgeCloudMutations` verifies every mutation exists unchanged in the local journal, writes a batch transactionally and avoids redundant receipt updates. Receipts are local sync metadata; they contain no pairing credentials. Account separation prevents another account from inheriting upload completion.

The delegate records acknowledgements for received records, saved records and exact immutable server conflicts. Restored pending saves whose fingerprints are already acknowledged are removed from engine state; empty outgoing pages do not schedule zone creation or send. Fetched acknowledgement writes are chunked to at most 250 records. Tests cover database restart, independent accounts, duplicate acknowledgements, rollback when a batch includes a missing event, equivocation rejection and a repeated complete scan returning no pending mutations. All 172 portable tests pass; CloudKit source parsing passes. Native SDK/CloudKit integration remains unverified, including the acknowledgement/checkpoint crash window and external journal-zone removal recovery. Content assets/metadata and background synchronization remain unfinished.

## Failure reporting

Cloud failure status now carries a typed category rather than an arbitrary error string: quota, network, account, temporary service, journal conflict, local persistence or other. Settings provides distinct localized recovery guidance for each. Delegate failure classification is retained when the enclosing sync operation subsequently throws a generic invalid-state error; direct account/fetch/send errors are also reported to the adapter and suspend it without removing local history. Portable tests cover local integrity/equivocation, malformed protocol, account confirmation, corrupt state, disk-full and unknown-error categories. All 173 core tests pass; app/delegate source parsing and localization coverage pass. Native CKError mapping, partial-failure aggregation, server retry-after/backoff and native fault injection still need validation/implementation.

Recovery references: [private quota errors](https://developer.apple.com/documentation/cloudkit/ckerror/code/quotaexceeded), [network unavailability](https://developer.apple.com/documentation/cloudkit/ckerror/code/networkunavailable), and [server retry-after guidance](https://developer.apple.com/documentation/cloudkit/ckerror/retryafterseconds).

## Retry deadlines

Account-bound cloud state now includes an optional durable retry deadline. Transient network/service/rate-limit/zone-busy failures disable the adapter and persist a delay, using a valid positive server retry-after value when supplied or 30 seconds otherwise. Enablement rejects attempts before that deadline and reports the time in Settings. Later failures cannot shorten an existing deadline; expiration clears it when enablement succeeds. Account changes/sign-out discard the previous account's deadline with its checkpoint. Existing version-1 JSON without the optional field remains decodable. Tests use an explicit clock to verify restart retention, attempted early retry, non-shortening, exact-deadline resume, checkpoint preservation and account separation. All 174 portable tests pass; source parsing passes. Native CloudKit error injection, partial failure aggregation, adaptive backoff/reachability and asset/metadata exchange remain unfinished.

## Validated content asset import

`CloudContentDescriptor` now carries version, SHA-256 content ID, kind, length and original filename for EPUB/course/font/dictionary assets. Its validation bounds filename/length, rejects path separators/NUL and requires the supported extension for each kind; firmware remains in the separate update path. `ContentImporter.importCloudAsset` uses the existing content inspectors against an immutable vault stage, derives metadata from validated bytes and retains the declared original filename for display/routing. Course details and locale are stored through the existing course metadata transaction.

The vault now supports expected ID/length constraints, verified on its streamed immutable copy before invoking the inspector or publishing the object. Hash/length mismatch and format rejection therefore write no library metadata and publish no invalid object. Tests cover descriptor Codable round trip, wrong hash/length, matching-hash corrupted course CRC, original-name preservation, derived locale, repeated import and path/kind mismatch rejection. The full suite passed 175 tests; after adding the final corruption assertion, all eight course tests pass. Native CKAsset records/upload/download, content descriptors in CloudKit, course-family association exchange, global deletion and native integration remain unfinished.

## CKAsset source integration

The private engine adapter now accepts the immutable vault and creates a shared validated importer. It scans active non-firmware content in bounded pages, queues `content-<sha256>` record identities in the existing private zone, and uploads `LilaContentV1` records with Bytes field `descriptor` and Asset field `asset`. Incoming assets are copied through immutable hash/length/format validation immediately, before event import/checkpoint persistence. Metadata is derived through the existing inspectors. Filenames are display aliases, not content identities.

Schema 17 stores bounded-operation content acknowledgements per account/hash/kind/length; accepted assets are skipped after restart, including renamed identical files. Cloud content acknowledgements validate local metadata and existing receipts transactionally. Conflict handling compares immutable identity/kind/length, explicitly fetches the complete server record because conflict copies may lack asset URLs, validates/imports its asset and then acknowledges it. Deletions still stop the adapter rather than erase causal history or implement incomplete global-removal semantics. Settings confirmation now states that content files are uploaded as well as journal records.

The full portable suite passed 177 tests; the final receipt guard passed both cloud content tests afterward. Native source parsing/localization pass. CloudKit code remains excluded from Linux type checking and has not run against an account. Native asset size/quota/error/crash testing, download staging lifetime, concurrent metadata aliases, course-family associations, global deletion propagation and background work remain unfinished. Add `LilaContentV1` with the descriptor/asset fields to the signed development container schema before native testing. ## Course-family persistence

`CloudCourseAssociation` defines a versioned exact-pack SHA/confirmed 16-byte family binding. Schema 18 durably retains incoming bindings even when the pack has not arrived. Acceptance checks existing associations, migration reservations and typed offline history claims; a conflicting family is rejected transactionally. Pending bindings constrain future history imports and prevent storing non-course content for that hash. They become confirmed associations only inside the validated course-pack metadata transaction. Duplicate bindings are harmless; removed course content keeps its identity but is omitted from bounded exports.

Tests cover binding-before-asset, restart, validation-gated activation, duplicate binding, conflicting family, export cursor/deletion filtering, malformed family/non-course rejection, and offline event conflicts in both arrival orders. All 180 core tests pass. CloudKit course record transport/acknowledgements are not yet wired; the app still accurately lists course associations as unsynchronized. Native SDK/account validation and global deletion propagation remain unfinished.

## Causal library visibility merge

`LibraryVisibilityChange` defines immutable version-1 removal/restore decisions with UUID identity, installation origin, exact content hash and at most 16 causal parents. `LibraryVisibilityHistory.merge` deduplicates identical changes, rejects equivocation/cycles/cross-content parents and computes complete causal heads. A concurrent removal wins over a restore; an explicit restore referencing every effective removal head supersedes them. Missing ancestors defer that change and descendants, preserving current effective heads until delivery completes. The baseline visibility can be retained when no complete head exists. Clocks and filenames do not determine visibility ordering.

Tests cover reversed/duplicate arrival, concurrent delete versus restore, observed restore convergence, missing ancestry, equivocation, cycles, cross-content ancestry and self-reference. All 183 core tests pass. This is the merge core: SQLite visibility journaling, legacy local marker migration, native delete/restore mutation integration, CloudKit records/acknowledgements and remote reader deletion remain pending. Existing local delete/restore behavior has not been replaced yet.

## Visibility event persistence

Schema 20 stores immutable visibility event payloads with UUID/content indexes. Import accepts at most 250 changes, validates duplicate identity consistency and the complete stored graph, and applies derived removal markers, reader deselection and pre-commit transfer abort requests in one transaction. Restoration clears only the removal marker. Missing-content changes remain journaled without writing a foreign-key marker until content exists. Export is bounded and ordered by UUID cursor. Tests verify reversed ancestry across database restart, duplicate delivery, equivocation rollback with another new change in the same batch, and derived removal. All 184 core tests pass.

Native local action journaling, backfilling legacy deletion markers, applying retained visibility on subsequent content import, CloudKit visibility records/acknowledgements and reader-side removal remain pending. Import currently validates the whole retained visibility graph; resource-indexed reconciliation is a future scaling improvement. The new persistence path is not yet enabled in the app or cloud adapter.

## Native visibility mutations

The app now uses `setLibraryVisibility` with its Keychain installation origin for remove/restore actions. The method reads effective heads and writes the new decision and derived effects under one SQLite immediate transaction, avoiding stale-head races between handles. Same-state actions avoid redundant events. An old marker with no complete journal head is first preserved as a removal event; restore then explicitly observes it. Files, metadata, reader deselection and existing abort intent retain their previous lifecycle behavior. Raw local marker APIs remain for legacy compatibility.

Tests verify old-marker restore creates the linked removal/restore pair, repeated restore adds no events and a later removal observes the restored head. All 185 core tests pass; native source parsing passes. Existing legacy markers still need backfill before cloud enablement, retained visibility needs application on subsequent content import, and CloudKit visibility records/receipts remain unwired. Native UI execution and reader-side removal are still pending.

## Content arrival visibility

Public library metadata writes now use an immediate SQLite transaction and reapply retained visibility for the exact content hash. Validated course metadata uses the same private transaction helper inside its existing pack transaction. A removal delivered before a missing asset therefore becomes a foreign-key deletion marker atomically when metadata arrives; a causally observed restore keeps it visible. Removed content metadata/files remain retained. The visibility side effects share the same helper as event import, preserving reader deselection and abort intent.

A new test imports removal/restore decisions before both content entries exist, reopens the database, stores metadata and verifies the removed item stays out of active library listings while the restored item remains visible. All 186 core tests pass. Cloud visibility transport/acknowledgements and legacy marker backfill remain pending, along with native/reader validation.

## Legacy removal backfill

Before explicit cloud synchronization starts, the app now obtains its Keychain installation origin and journals legacy removal markers in bounded batches. Each immediate transaction selects only removed entries with no visibility history, creates immutable root removal decisions and applies existing removal effects. Restarted or repeated backfill skips journaled entries. The async caller checks cancellation between committed batches and does not start CloudKit fetch/send until backfill completes.

Tests cover a one-entry batch limit, database reopening between batches, zero further events on completion, retention against an unobserved remote restore and successful explicit observed local restore. All 187 core tests pass; app syntax parsing passes. Cloud visibility records/acknowledgements, native CloudKit/UI execution and reader-side removal remain pending.

## Foreground resume

The app now attempts cloud synchronization on startup and transition to an active scene, only when persisted cloud state remains explicitly enabled. The delegate verifies the actual account still matches the enabled account before returning a resumable identity; changed accounts disable/reset state and require confirmation. Disabled or delayed state does not resume. A shared model operation retains the same legacy backfill, overlap gate, synchronization and library reload as the explicit Settings action; its busy guard prevents overlapping foreground/manual attempts. Saved-history footers now point to private cloud setup while keeping reader history exchange explicitly unfinished.
